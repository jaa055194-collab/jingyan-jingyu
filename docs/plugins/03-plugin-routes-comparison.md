# 鲸言鲸语 · 用户插件技术路线对比（A / B / C）

> 目的：在选定插件形态前，把三条技术路线讲清楚，并逐条对照本项目现状与既有设计约束。

## 0. 先看项目现状（这决定了很多前提）

- **插件代码现状**：`packages/jingyu_client_kit` 里只有"插件契约 + 内存宿主"——`PluginManifest`（清单）、`ClientPlugin`（插件入口）、`PluginHost.load()`（接收**已在内存里构造好的 Dart 对象**）。**没有**从磁盘/`plugin.json`/zip 读取插件的代码，**没有**任何真实插件实现，仓库里**没有一个 `plugin.json`**。
- **没有客户端 App**：主干上只有 `apps/host`（服务端）；真正的客户端外壳 M11 是**尚未合并的草稿 PR #8**，且它也只 `new` 了 `PluginHost`、从不 `load`，消息卡片/设置分区等插件界面都没接。
- **既有的设计约束（很关键）**：
  - `docs/plugins/01-plugin-spec.md` 规定插件是 `plugins/<id>/` 下的 **Dart 源码**（`plugin.json` + `lib/plugin.dart` + `assets` + `test`），**随 App 一起编译**；§5 还明确"**插件不能下载或执行代码**"。
  - `docs/architecture/01-layering.md`：`client_kit` 不得依赖 Flutter，UI 只在 `apps/client_flutter`（由 M11 创建）。
  - `FR-60 斜杠指令`、`FR-35 房间生成` 是现有的插件扩展点；`FR-38/39` 里写了模型包"安全解包"（Zip Slip / 扩展名白名单 / 体积与条目上限 / 压缩比 / JSON 深度），但目前**未实现**（M10 未交付）。
  - 项目定位是**自用小圈子、非商业**（FR-02）——这会影响"要不要为陌生人做重安全沙箱"。

**一句话结论**：现有插件只是"编译期代码契约"，做不到"用户自研插件即插即用、zip 分享给别人装"。要达成必须选定一种**可分发、可安装的插件形态**，下面是三条路线。

---

## 路线 A：声明式 / 数据插件包（推荐用于"朋友下载就能用"）

**核心思路**：插件包是**纯数据**（zip 里只有 JSON 与素材，没有可执行代码），由 App **内置的插件运行时**去解释。

**包结构（zip 示例）**
```
my-plugin/
  plugin.json          # id / name / version / apiVersion / capabilities / platforms / assetCredits
  slash_commands.json  # 指令名、描述、requiresAiCapability、动作=调用哪个宿主工具/提示词
  cards/*.json         # 消息卡片模板（数据 → 界面声明，不写代码）
  settings/*.json      # 设置分区 schema（字段类型 / 校验 / 默认值）
  rooms/*.json         # 房间布局 RoomLayout（配合 M10 世界）
  assets/...           # 图片、音效（带署名）
  README.md
```

**怎么"接入"**：App 内置一个声明式运行时（纯 Dart，放 `client_kit`），读取 `plugin.json` 和上述数据，把它们注册成 `SlashCommand` / 消息卡片 / 设置分区 / 房间生成器。**全程不加载、不执行任何下载来的代码**。

**怎么"分享/安装"**：
- 打包：`tool/pack-plugin` 把目录打成 zip（校验清单、算 sha256）。
- 安装：**安全解包**（复用 FR-39 已定义的规则：Zip Slip 防护、扩展名白名单、条目数/解压体积上限、压缩比与 JSON 深度限制、拒绝 `.js/.exe/.dll/.so` 等）→ **严格 schema 校验** → 存入本地插件库 → 启用。
- 导出 = 反向打包，天然支持"把我的插件发给朋友"。

**结合项目落地位置**：新增 `client_kit/plugin_package.dart`（包模型+校验）、声明式运行时；`apps/client_flutter` 增加插件管理页（导入/导出/启用/停用）；服务端可选做插件包分发。

**依赖前置**：导入/导出/管理 UI 需要 **M11 客户端外壳**先落地。

**工作量**：中（数据 schema + 运行时解释 + 安全解包 + UI），跨 `client_kit / client_flutter`。

**优点**：真正做到"下载 zip 就装好"，安全，用户不必会写代码；与"不执行下载代码"的既有原则一致。
**缺点**：能力被限定在预设扩展点内，跑不了任意自定义逻辑；需要先把 schema 定清楚。

---

## 路线 B：源码插件包（开发者向，改动最小）

**核心思路**：沿用现有规范——插件就是 `plugins/<id>/{plugin.json, lib/plugin.dart, assets, test}` 的 Dart 源码，打成 zip 分享。

**怎么"接入"**：把 zip 解压进仓库 `plugins/` 目录，**重新编译客户端**（`flutter build`）。可在 `tool/` 加 `pack-plugin` / `install-plugin` 脚本，再在启动时扫描 `plugins/` 生成注册表交给 `PluginHost.load`。

**怎么"分享"**：zip 分发源码；对方解压进源码树后**自己重新构建 App**。

**结合项目落地位置**：`apps/client_flutter` 启动时装配插件（PR #8 已经把 `PluginHost` 建好了，差"扫描目录→注册表→load"这一步）；`tool/` 脚本；`plugins/` 目录。

**依赖前置**：M11；对方有 Dart/Flutter 构建环境。

**工作量**：小（契约已存在，主要补装配代码 + 打包脚本）。

**优点**：改动最小、能力最强（能写任意逻辑）、完全契合现有契约。
**缺点**：朋友必须会开发、装环境、重新编译；每次更新都要重编——**达不到"普通用户下载即用"**；对朋友端有执行任意代码的风险（自建小圈子可控）。

---

## 路线 C：WebView / JS 沙箱插件（能力最强、风险最大）

**核心思路**：插件是 JS/HTML 包（zip），跑在 WebView / WebView2 里，通过受限 bridge 调宿主能力（发消息、调模型等）。

**项目已有基础**：M10 本就计划用 WebView（Android）/ WebView2（Windows）承载 3D 房间页（见 `docs/plugins/02-assets.md`），有现成的承载经验。

**怎么"接入/分享"**：zip 内含 JS/HTML；安装后加载进 WebView，靠 bridge 与宿主通信。

**结合项目落地位置**：新增 bridge 协议（`jingyu_protocol`）、`client_flutter` 的 WebView 宿主与能力网关。

**依赖前置**：M11 + WebView 集成。

**工作量**：最大（bridge 协议、双端 WebView 一致性、能力网关、沙箱策略）。

**优点**：可跑自定义 UI 与逻辑，像"小程序"生态，扩展性最好。
**缺点**：安全面最大，且与现有"禁 eval / 不执行下载代码"原则**直接冲突**（要重新定安全策略）；Android WebView 与 Windows WebView2 行为不一致，跨端成本高。

---

## 三条路线横向对比

| 维度 | A 声明式数据包 | B 源码插件包 | C WebView/JS 沙箱 |
|---|---|---|---|
| 朋友"下载即装" | ✅ 能 | ❌ 需重编 | ✅ 能（但需沙箱） |
| 是否需要开发环境 | 不需要 | 需要 | 不需要 |
| 能力上限 | 限定扩展点内 | 最强（任意 Dart） | 强（任意 JS/UI） |
| 安全风险 | 低（不执行代码） | 中（信任源码） | 高（执行 JS） |
| 是否契合现有设计 | ✅ 很契合 | ✅ 完全契合 | ❌ 冲突（禁执行代码） |
| 前置依赖 | M11 外壳 | M11 + 构建环境 | M11 + WebView |
| 工作量 | 中 | 小 | 大 |
| 适合 | 面向朋友的分享 | 内部/开发者自研高级插件 | 追求生态化、可接受风险 |

---

## 结合本项目的建议

1. **主推 A，B 作为补充**：A 用来满足"用户自研插件以压缩包分享、别人下载就能用"的诉求，安全且不需要用户会写代码；B 用来满足"高级开发者要写任意逻辑"的内部/自研场景。两者可并行。
2. **关键前置是 M11 客户端外壳**：没有它就没有承载插件、导入导出插件的界面，无论 A/B/C 都缺"接入点"。
3. **可以现在就先推进、且不依赖 M11 的部分**（建议先做，等外壳好了直接接 UI）：
   - 定 **声明式插件包 schema v1**；
   - 实现 **插件包解析 + 安全解包校验**（Zip Slip / 白名单 / 体积与条目上限 / 压缩比 / JSON 深度，纯 Dart + 单测）；
   - 写 **打包脚本** `tool/pack-plugin`；
   - 端到端单测：打包 → 导入 → 校验 → 由内置声明式运行时注册到 `PluginHost`。
   这样"插件以压缩包分享并被安全接入"的核心链路可以先跑通、先验证。
4. **C 暂不建议**：除非明确要走"插件生态/小程序"路线，并愿意重定安全策略、承担双端 WebView 成本。

---

*说明：以上为技术路线对比，供选型决策；目前尚未改动代码。*
